<Summary>
    The <Link href="https://github.com/CoherentLabs/Gameface-MCP">Gameface MCP server</Link> connects a coding agent to a running Gameface Player through the <Highlight>Chrome DevTools Protocol</Highlight>.

    Once connected, the agent reads Gameface's own warnings, inspects the DOM it produced, captures screenshots, and checks that text fits inside its box, rather than describing what it expects to have built.
</Summary>

## Why a Live Engine Is Required

Without a connection, every iteration routes through a person. The agent writes markup, someone runs the Player or Game, someone describes what looks wrong, and the agent revises. What the agent never observes is what Gameface did with its code—the information that settles the question.

The console is the clearest signal. Gameface warns about CSS it cannot resolve, diagnosing Gameface-specific bugs faster than any other available feedback. That warning means nothing while it sits unread.

:::note[Designed for the Gameface Player]

The server connects to any engine running the Gameface SDK through the Chrome DevTools Protocol. However, it was developed with the Gameface Player in mind, so other engines may not behave as expected. Every connection is verified over CDP, and `navigator.userAgent` must contain `cohtml`.

:::

## Prerequisites

* **Node.js 18+**, since the server uses the global `fetch` API.
* **A local Gameface SDK with a Player executable.** The repository does not ship one, so a Gameface licence and SDK are required. On Windows the executable normally sits at `.../Player/Player.exe`. Note that `Player.exe` lives in a `Player` subfolder under the SDK root rather than at the root itself.
* **Gameface 3.1.2 or newer**, for the reasons covered in [Version Awareness](#version-awareness).

## Installing

<Steps>

1. #### Install the server

    <Link href="https://www.npmjs.com/package/add-mcp">add-mcp</Link> detects the
    installed agents and writes the server into each one's config.

    <Tabs>
    <TabItem label="Global (recommended)">

    Available in every project on the machine:

    ```bash
    npx add-mcp "npx -y gameface-mcp@latest" --name gameface -g
    ```

    </TabItem>
    <TabItem label="Project only">

    Run from the project folder:

    ```bash
    npx add-mcp "npx -y gameface-mcp@latest" --name gameface
    ```

    </TabItem>
    </Tabs>

    :::caution[Install Once, Not Both]

     A project `gameface` MCP entry and a global gameface MCP entry compete instead of merging, and only one runs.

    :::

2. #### Set up the Player

    Start the agent and ask it to launch the Gameface Player. On first launch it
    asks for the Player path (`Player.exe`, its folder, or the SDK folder) or
    offers to search the machine. The path is saved to
    `~/.gameface-mcp/config.json` and reused by every project.

    :::tip[Disable Player Chrome Before Measuring]

    The Player's toolbar and bookmark bar take an inconsistent part of the
    requested height, so screenshots and layout assertions measure the wrong
    canvas. Add `"browserArgs": ["--enable-gui=false"]` to
    `~/.gameface-mcp/config.json` to remove them.

    If you let the agent launch the player and write the config, it will automatically add the `"browserArgs": ["--enable-gui=false"]` entry for you.

    :::

3. #### Install the Conductor skill (optional)

    The Gameface UI Conductor skill clarifies requirements, gets sign-off on a
    spec, then implements and validates with the MCP tools:

    ```bash
    npx skills add CoherentLabs/Gameface-MCP --agent claude-code -g
    ```

    Drop `-g` to install into the current project only. Start a new session afterwards.

    :::tip[Specify the Client]
    Use the `--agent` flag to specify which client should use the skill. For example, `--agent claude-code` installs the skill for the Claude Code client.
    :::

</Steps>

## Client Configuration

`add-mcp` writes the following entry for each detected client. No manual editing is needed.

<Tabs>
<TabItem label="Claude Code">

Global: `~/.claude.json`. Project: `.mcp.json`.

```json title=".mcp.json"
{
  "mcpServers": {
    "gameface": {
      "command": "npx",
      "args": ["-y", "gameface-mcp@latest"]
    }
  }
}
```

</TabItem>
<TabItem label="VS Code / Copilot">

Global: user `mcp.json`. Project: `.vscode/mcp.json`.

```json title=".vscode/mcp.json"
{
  "servers": {
    "gameface": {
      "command": "npx",
      "args": ["-y", "gameface-mcp@latest"]
    }
  }
}
```

VS Code uses `servers` instead of `mcpServers`.

</TabItem>
<TabItem label="Gemini CLI">

Global: `~/.gemini/settings.json`. Project: `.gemini/settings.json`.

```json title=".gemini/settings.json"
{
  "mcpServers": {
    "gameface": {
      "command": "npx",
      "args": ["-y", "gameface-mcp@latest"]
    }
  }
}
```

:::tip[Raise the Timeout]

The automatic Player search can take up to a minute plus prompt time, all in
one tool call. Add `"timeout": 90000` to the entry.

:::

</TabItem>
<TabItem label="Claude Desktop">

`%APPDATA%/Claude/claude_desktop_config.json` on Windows,
`~/Library/Application Support/Claude/claude_desktop_config.json` on macOS.

```json title="claude_desktop_config.json"
{
  "mcpServers": {
    "gameface": {
      "command": "npx",
      "args": ["-y", "gameface-mcp@latest"]
    }
  }
}
```

</TabItem>

:::note[Server Flags]

Flags go inside the quoted command, after the package name, for example
`npx add-mcp "npx -y gameface-mcp@latest --port 9445" --name gameface -g`.
Flags override `~/.gameface-mcp/config.json`.

:::

## Available Capabilities

### Managing Players with Commands

Commands are shortcuts for launching and managing Players mid development. They
appear as slash commands, in Claude Code as `/mcp__gameface__<command>`. Arguments
are positional, and `true`, `yes`, `y` and `1` all count as yes.

#### Launching

<Tabs>
<TabItem label="Default Player">

```text
/mcp__gameface__launch-player
/mcp__gameface__launch-player http://localhost:3000
```

Launches the default Player, optionally opening a URL.

</TabItem>
<TabItem label="Pick a Player">

```text
/mcp__gameface__launch-player true
```

Lists every configured Player, sorted by version, and launches the selected one.
Useful for testing a UI against several Gameface versions.

</TabItem>
</Tabs>

#### Adding Players

<Tabs>
<TabItem label="Scan the machine">

```text
/mcp__gameface__scan-players
```

Runs a search script inside the server and adds every Player found. The agent
only sees the resulting list, not your files. The default Player is unchanged.

</TabItem>
<TabItem label="Add a folder">

```text
/mcp__gameface__add-player
```

Skips the scan. Provide a `Player.exe` or a folder of Players, and every Player
inside is added. The default Player is unchanged.

</TabItem>
</Tabs>

#### Changing the Default

`/mcp__gameface__change-player-path` asks for a new default Player path. Pass
`true` to search the machine instead.

:::tip[Listing the Commands]

Most clients list every available command after typing `/gameface`. The prefix
matches the `--name` used at install time.

:::

### Tools

These tools are rarely invoked by hand. Knowing what exists establishes what can
reasonably be requested, and what to demand evidence of.

### Reading What Gameface Did

| Tool | Function |
| --- | --- |
| `get_console_logs` | Buffered console output plus Log-domain entries, including unsupported-feature warnings |
| `get_computed_styles` | Computed CSS for a node, meaning what Gameface kept rather than what was written |
| `get_dom_tree` / `search_dom` | Snapshot of the DOM, or nodes matching a text or XPath query |
| `take_screenshot` | Full page, viewport, or a custom clip rect |
| `eval_js` | Runs JavaScript in the connected page |
| `interact_element` | Click, type, hover, focus, scroll into view, or touch |


### Checking Layout

| Assertion | Check performed |
| --- | --- |
| `assert_text_fits` | Whether an element's content overflows its own box |
| `assert_no_overlap` | Whether two elements' rendered boxes intersect |
| `assert_within_parent` | Whether an element stays inside its parent, an ancestor, or the viewport |


### Measuring Cost

`perf_lint` is a static check for expensive layout patterns like `align-items: stretch`, unsized flex items, and misuse of `display: simple`. No timing involved, so it does not flake.

`perf_measure` runs a fixed frame-timing scenario and reports p50, p95, and p99 against a recorded baseline.

:::note[What a perf_measure Number Compares Against]

The baseline is a noise floor recorded at 1920x1080 across five runs of 600 frames,
with the Player restarted between runs. Treat a result as a signal that a screen is
unusually expensive rather than as a substitute for profiling a real UI under real
game load. See
[Performance and Memory Profiling](/polishing/debugging-profiling--testing/performance-and-memory-profiling/)
for that.

:::

### Reading the Documentation

Alongside the tools, the server exposes the documentation corpus and the engine
constraints as MCP resources, `gameface://code-instructions` and
`gameface://rag/<file>.md`. The [next article](/building-with-ai/grounding-the-agent/)
covers both.

## Version Awareness

Gameface <Highlight>3.1.2</Highlight> or newer is required. This version introduced CDP protocol support, including engine logs through the Chrome DevTools Protocol.

The minimum version is verified at connection time via `cohtmlVersion`. Some older versions have CDP quirks that the server works around, but a tool returning unexpected output may indicate an engine-side gap.

## Confirming the Connection

Ask the agent to launch the Player and screenshot the current view. An image and a
`cohtmlVersion` returning together confirm a live connection. A description of what
the agent *expects* the screen to look like means the server is not connected.
