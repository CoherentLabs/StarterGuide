<Summary>
    The <Link href="https://github.com/CoherentLabs/Gameface-MCP">Gameface MCP server</Link> connects a coding agent to a running Gameface Player through the <Highlight>Chrome DevTools Protocol</Highlight>.

    Once it is connected the agent can read the engine's own warnings, look at the DOM it just produced, screenshot the result, and check that text fits inside its box, instead of describing what it expects to have built.
</Summary>

## Why the agent needs a live Player

Every iteration routes through you when the agent has no connection. It writes
markup, you run the Player, you describe what looks wrong, and it revises. What
the agent never gets to see is what the engine did with its code, which is the one
piece of information that would settle the question.

Take the console. Gameface warns about CSS it cannot resolve, and that warning
diagnoses a Gameface-specific bug faster than anything else available. It does
nobody any good while it sits unread in the Player.

:::danger[Gameface Player only, by design]

The server refuses to launch or connect to anything that is not Gameface Player.
Every connection gets verified over CDP, where `navigator.userAgent` must contain
`cohtml`, and anything else is killed. This is not a general browser-automation
server and should not be repurposed into one.

:::

## Prerequisites

* **Node.js 18+**, because the server uses the global `fetch` API.
* **A local Gameface SDK with a Player executable.** The repository does not ship
  one, so you need your own Gameface licence and SDK. On Windows the executable
  normally sits at `.../Player/Player.exe`. Note that `Player.exe` lives in a
  `Player` subfolder under the SDK root, not at the root itself.
* **Gameface 3.1.2 or newer**, for reasons covered in
  [Version awareness](#version-awareness).

## Installing

<Steps>

1. #### Clone and build

    ```bash
    git clone https://github.com/CoherentLabs/Gameface-MCP.git
    cd Gameface-MCP
    npm install
    npm run build
    ```

    The build compiles `src/` into `build/`, producing `build/index.js`. That path
    is what every client config points at.

2. #### Point it at your Player

    Create `~/.gameface-mcp/config.json`. This file belongs to your machine rather
    than to a project, because the server gets reused across every game repository
    you work in:

    ```json title="~/.gameface-mcp/config.json"
    {
      "browserExecutable": "D:/path/to/your/sdk/Player/Player.exe",
      "browserArgs": ["--enable-gui=false"],
      "port": 9444,
      "cdpHost": "localhost"
    }
    ```

    Every field is optional, and `browserArgs` are merged into every launch.

    :::tip[Turn the Player chrome off before you measure anything]

    The Player's toolbar and bookmark bar consume an inconsistent slice of the
    height you asked for, so the real viewport never matches your requested
    resolution. Every screenshot and layout assertion is then measured against the
    wrong canvas. Setting `--enable-gui=false` removes them.

    :::

3. #### Wire it into your agent

    Pick your client below. If you created the config file in step two, the `args`
    array needs nothing beyond the path to `build/index.js`, since the Player path
    and port are picked up automatically.

</Steps>

## Client configuration

<Tabs>
<TabItem label="Claude Code">

Create `.mcp.json` at your project root:

```json title=".mcp.json"
{
  "mcpServers": {
    "gameface": {
      "command": "node",
      "args": ["/absolute/path/to/Gameface-MCP/build/index.js"]
    }
  }
}
```

</TabItem>
<TabItem label="VS Code / Copilot">

Create `.vscode/mcp.json` at your project root. The repository already ships one
you can copy:

```json title=".vscode/mcp.json"
{
  "servers": {
    "gameface_local": {
      "command": "node",
      "args": ["build/index.js"]
    }
  }
}
```

:::caution[The top-level key differs here]

VS Code expects `servers`, not `mcpServers`. Copying a config from another client
without changing this key fails quietly, and the server simply never appears in
the tool list.

:::

</TabItem>
<TabItem label="Gemini CLI">

Use `.gemini/settings.json` for a single project, or `~/.gemini/settings.json` to
apply it everywhere:

```json title=".gemini/settings.json"
{
  "mcpServers": {
    "gameface": {
      "command": "node",
      "args": ["/absolute/path/to/Gameface-MCP/build/index.js"],
      "timeout": 30000,
      "trust": false
    }
  }
}
```

</TabItem>

## What the agent can do once connected

You will rarely call these yourself. Knowing what exists tells you what you can
reasonably ask for, and what to demand evidence of.

### Reading what the engine did

| Tool | What it does |
| --- | --- |
| `get_console_logs` | Buffered console output plus Log-domain entries, including the engine's unsupported-feature warnings |
| `get_computed_styles` | Computed CSS for a node, meaning what the engine kept rather than what you wrote |
| `get_dom_tree` / `search_dom` | Snapshot of the DOM, or nodes matching a text or XPath query |
| `take_screenshot` | Full page, viewport, or a custom clip rect |
| `eval_js` | Runs JavaScript in the connected page |
| `interact_element` | Click, type, hover, focus, scroll into view, or touch |

The first two are the ones to know about, and they approach the same question
from opposite sides. `get_console_logs` reports what the engine rejected outright,
while `get_computed_styles` shows you the survivors, which is how an agent
discovers that the `padding: var(--space-md)` it just wrote computes to `0px`.
Gameface-specific bugs tend to live in that gap between the code an agent wrote
and the styles the engine kept.

### Checking the layout

| Assertion | What it checks |
| --- | --- |
| `assert_text_fits` | Whether an element's content overflows its own box |
| `assert_no_overlap` | Whether two elements' rendered boxes intersect |
| `assert_within_parent` | Whether an element stays inside its parent, an ancestor, or the viewport |

A screenshot review will not reliably catch a label clipped by two pixels or a
tooltip sitting over the value it describes. These will.

### Measuring cost

`perf_lint` is a static check for layout patterns the Gameface documentation names
as expensive, such as `align-items: stretch`, unsized flex items, and misuse of
`display: simple`. No timing is involved, so it never flakes.

`perf_measure` runs a fixed frame-timing scenario against the live connection and
reports p50, p95, and p99 against a recorded baseline.

:::note[What a perf_measure number is actually comparing against]

The baseline is a noise floor recorded at 1920x1080 across five runs of 600
frames, with the Player restarted between runs. Treat a result as a signal that a
screen is unusually expensive, not as a substitute for profiling your real UI
under real game load. See
[Performance and Memory Profiling](/polishing/debugging-profiling--testing/performance-and-memory-profiling/)
for that.

:::

### Reading the docs

Alongside the tools, the server exposes the documentation corpus and the engine
constraints as MCP resources, `gameface://code-instructions` and
`gameface://rag/<file>.md`. The [next article](/building-with-ai/grounding-the-agent/)
covers both.

## Version awareness

CDP support has changed across Gameface versions. `launch_browser`,
`connect_browser`, and `gameface_get_status` all report the connected
`cohtmlVersion` and warn below the recommended minimum of
<Highlight>3.1.2</Highlight>, which introduced additional CDP protocol support.

Clearing that minimum does not mean everything behaves. Our own development SDK
is 3.2.0.2, comfortably above it, and it still has quirks the server works
around:

* `DOM.resolveNode` returns an empty object instead of a usable reference, with no
  error.
* `DOM.setAttributeValue` silently no-ops.
* `DOM.performSearch` never returns a search ID, which makes `search_dom` less
  dependable than the other inspection tools.

The assertion tools sidestep the first two by resolving nodes through
`DOM.getBoxModel` and `document.elementFromPoint`. Read the list as what we have
hit and fixed so far, not as a complete account. If a tool ever returns something
that makes no sense, suspect an engine-side CDP gap before you suspect your own
code.

## Confirming it works

Ask your agent to launch the Player and screenshot your current view. An image
and a `cohtmlVersion` coming back means the connection is live. If instead you get
a description of what the agent *expects* the screen to look like, the server is
not connected and you are still guessing.
