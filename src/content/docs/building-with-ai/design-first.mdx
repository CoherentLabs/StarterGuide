## What actually goes wrong

The failures are not ugly. That is what makes them easy to miss in a review of any
single component. They are failures of *consistency*, and they only become obvious
once you look at the whole screen:

* **Color drift.** Four shades of "the accent color", none of them the same
  value, because each was picked in a different conversation.
* **No hierarchy.** Every panel styled with the same weight, so nothing tells the
  player what matters. Or the reverse - every element competing, everything
  glowing.
* **Arbitrary spacing.** `12px` here, `0.8rem` there, `14px` in the third panel.
  Individually fine, collectively noisy.
* **Semantic collisions.** Red used for a damage number in one screen and for a
  decorative border in another, so the player learns nothing from it.
* **Type soup.** Five font sizes that differ by two pixels, and body copy set at
  whatever looked right in that component's context.

None of this is an engine problem, and none of it is caught by an assertion or a
lint rule. It is what happens when hundreds of small visual decisions get made
independently, by something with no memory of the previous ones and no opinion
about the whole.

:::note[The agent is doing exactly what you asked]
When you say "build a settings panel" without a design system, you have asked for
a settings panel *and* a visual language for it. It will deliver both. The second
one is the problem.
:::

## Define the system before you prompt

The fix is unglamorous: decide the visual rules first, write them down as code,
and let the agent spend its judgment on layout and behavior instead of on taste.

Here is what is worth having in place before the first UI prompt.

### Color, with meaning attached

Not just a palette - a palette where each color has a *rule*. This is the part
agents follow surprisingly well and will never invent on their own.

The design brief for one of our test builds stated it directly, and the
implementation held to it across eight screens:

> **Semantic rule (enforce this):** vermilion = danger or irreversible;
> ultramarine = sacred/arcane; verdigris = alive/complete; gold = earned.
> Never use gold for mere decoration on interactive elements the player has not
> unlocked.

A game UI version of the same idea, from a different project's tokens:

```scss title="src/assets/scss/_variables.scss"
// Accent - emphasis, "give this importance"
$accent: #90E8F1;
$accent-glow: rgba(#90E8F1, 0.30);

// Interactive - controls the player can operate
$interactive: #4B9FFF;

// Outline - structural chrome: grid, nav, tooltip
$outline: #8dc1c1;

// States
$error: #E05C72;
$warning: #E8A84A;
$success: #59F46B;

// Backgrounds, deepest to nearest
$bg-deep: #06090F;
$bg-surface: #0C1522;
$bg-elevated: #0f1e30;
$bg-overlay: #192C3E;
```

The comments are not decoration - they are the part the agent reads. A token named
`$accent` with "emphasis, give this importance" next to it gets used correctly.
A token named `$blue2` gets used at random.

### Typography as roles, not sizes

Define what each face and size is *for*, then the scale. An agent given "Cinzel
for anything carved or titled, EB Garamond for read text, IM Fell for scribal
labels and metrics" will place them correctly in components you never described.

Pin down the boundaries too - a minimum size, and what body copy may never drop
below. Left open, this is where an agent quietly ruins legibility on a TV.

See [Importing Fonts and Styling Text](/layout-assets-and-styling/texts--fonts/importing-fonts-and-styling-text/)
and [Auto-scaling Text](/layout-assets-and-styling/texts--fonts/auto-scaling-text/).

### Spacing, radius, borders and shadow

The four that decay fastest without rules. Give each one a closed set:

* **Spacing** - a scale, not free choice. Panel gaps, list-row padding, page
  margins.
* **Radius** - our clearest example specified *"border radius: 0 everywhere except
  circles"*. Blunt, memorable, and impossible to drift from.
* **Borders** - a hierarchy. "1px hairline for internal rules, 2px for panels, 3px
  for outer frames, dashed for empty or locked."
* **Shadow** - the one to constrain hardest, because it is where AI-generated UI
  goes to die. The same brief allowed exactly two kinds of shadow and no colored
  glows except one specific case. That single constraint did more for coherence
  than any amount of per-component review.

### The unit and resolution model

Decide whether you are working to a fixed design canvas or a fluid layout, and in
what unit, before anything is built. Retrofitting this across a finished UI is
a rewrite. See [Building Responsive Game UI](/layout-assets-and-styling/styling--scalability/building-responsive-game-ui/)
and [Handling Aspect Ratios with Media Queries](/layout-assets-and-styling/styling--scalability/handling-aspect-ratios-with-media-queries/).

## Write it as code, not as prose

A design system described in a chat message lasts until the context is trimmed.
The same system written into `_variables.scss` is read fresh every time the agent
opens the file, and - more usefully - is something you can point at: *"use the
existing tokens."*

Put it where the project already keeps such things, and reference it in your
project instructions. See [Managing Variables](/layout-assets-and-styling/dynamic-styling--variables/managing-variables/)
and [Writing Maintainable CSS](/layout-assets-and-styling/styling--scalability/writing-maintainable-css/).

:::caution[The `var()` shorthand trap bites design systems hardest]
A token-driven system is exactly the code that wants to write
`padding: var(--space-md) var(--space-lg)` and `border: 1px solid var(--color-border)`.
Gameface does not resolve `var()` inside a shorthand - the whole declaration is
dropped. Use the longhands, or use a preprocessor variable that is
substituted at build time rather than resolved at runtime. This is in the
[negative ruleset](/building-with-ai/grounding-the-agent/#the-negative-ruleset)
for a reason.
:::

## If you do not have a design yet

You still have options, in rough order of how well they worked for us:

1. **A real design handed off with tokens.** A designer's file plus a written
   token list is the best input by a distance. Our full-UI test started from a
   design created in <Link href="https://claude.com/product/design">Claude Design</Link>
   accompanied by a handoff document - palette with semantic rules, three type
   roles with a size scale, exact spacing and geometry, and six named recurring
   ornaments. The agent's job was then translation, not invention, and the result
   held together across eight screens.
2. **An existing screen to match.** If your project already has one good screen,
   say so explicitly and point at the file. Agents extrapolate an existing system
   far better than they originate one.
3. **A reference image.** Better than nothing, and agents read layout and hierarchy
   from an image well. They read *fine* visual detail from one much less well - see
   the [Match Tactics case study](/building-with-ai/in-practice/a-screen-in-an-existing-ui/),
   where the interaction model came out right the first time and the visual pass
   did not.
4. **Ask the agent to propose a system first, then freeze it.** As a separate
   step, before any component work: have it produce a token file, review it
   yourself, correct it, commit it. The value is not that the proposal is good -
   it is that afterwards there *is* a system, and everything downstream is
   consistent with it.

The one option that reliably fails is starting from nothing and hoping coherence
emerges. It does not.
