## The problem is consistency, not quality

Individual components come out fine, which is what makes this so hard to catch in
review. The problems only show up once you look at a whole screen, or at two
screens side by side.

Colors drift, so you end up with four shades of "the accent color" and no two the
same value, because each was chosen in a different conversation. Hierarchy
flattens, with every panel carrying the same visual weight, or the opposite,
where everything glows and competes. Spacing goes arbitrary: `12px` in one panel,
`0.8rem` in the next, `14px` in the third. Semantics collide when red means a
damage number on one screen and a decorative border on another, so the player
learns nothing from it. Type turns to soup, with five sizes two pixels apart and
body copy set to whatever looked right in that component's context.

None of this is an engine problem, and no assertion or lint rule will catch it.
Hundreds of small visual decisions get made independently by something that has no
memory of the earlier ones and no opinion about the whole.

:::note[The agent is doing exactly what you asked]

Asking for "a settings panel" with no design system in place is really asking for
two things, a settings panel and a visual language to render it in. You will get
both, and the second one is where the trouble starts.

:::

## Decide the rules, then write them as code

Before the first UI prompt, close off the decisions you do not want an agent
making, so that its judgment goes into layout and behavior rather than taste.

### Color, with meaning attached

A palette on its own is not enough, because each color also needs a rule. Agents
follow rules like these well and never come up with them unprompted.

One of our test builds stated its rules in the design handoff, and the
implementation held to them across eight screens:

> **Semantic rule (enforce this):** vermilion = danger or irreversible;
> ultramarine = sacred/arcane; verdigris = alive/complete; gold = earned.
> Never use gold for mere decoration on interactive elements the player has not
> unlocked.

A game UI version of the same idea lives in the token file of a different project.
Pay attention to the comments, since those are the part the agent reads:

```scss title="src/assets/scss/_variables.scss"
// Accent: emphasis, "give this importance"
$accent: #90E8F1;
$accent-glow: rgba(#90E8F1, 0.30);

// Interactive: controls the player can operate
$interactive: #4B9FFF;

// Outline: structural chrome, grid, nav, tooltip
$outline: #8dc1c1;

// States
$error: #E05C72;
$warning: #E8A84A;
$success: #59F46B;

// Backgrounds, deepest to nearest
$bg-deep: #06090F;
$bg-surface: #0C1522;
$bg-elevated: #0f1e30;
$bg-overlay: #192C3E;
```

A token named `$accent` with "give this importance" beside it gets used correctly.
A token named `$blue2` gets used at random.

### Typography as roles

Define what each face is for before you define its sizes. An agent told "Cinzel
for anything carved or titled, EB Garamond for read text, IM Fell for scribal
labels and metrics" places all three correctly in components you never described.

Pin the boundaries too, meaning a minimum size and a floor that body copy may
never drop below. Leave that open and you will find out later, on a TV, that
nothing is legible from the couch. See
[Importing Fonts and Styling Text](/layout-assets-and-styling/texts--fonts/importing-fonts-and-styling-text/)
and [Auto-scaling Text](/layout-assets-and-styling/texts--fonts/auto-scaling-text/).

### Spacing, radius, borders, and shadow

These four decay fastest without rules, so give each of them a closed set instead
of guidance.

Spacing needs a scale rather than free choice, covering panel gaps, list-row
padding, and page margins. Radius does better the blunter you make it, and our
clearest example simply said *"border radius 0 everywhere except circles"*, which
leaves nothing to drift toward. Borders need a hierarchy, such as 1px hairlines
for internal rules, 2px for panels, 3px for outer frames, and dashed for empty or
locked slots.

Shadow deserves the tightest constraint of the four, because uncontrolled glow is
where generated game UI usually goes wrong. The same handoff allowed exactly two
kinds of shadow and no colored glows except in one specific case, and that one
rule did more for coherence than any amount of per-component review.

### The unit and resolution model

Settle whether you are working to a fixed design canvas or a fluid layout, and in
what unit, before anything gets built. Retrofitting this across a finished UI is a
rewrite rather than a refactor. See
[Building Responsive Game UI](/layout-assets-and-styling/styling--scalability/building-responsive-game-ui/)
and [Handling Aspect Ratios with Media Queries](/layout-assets-and-styling/styling--scalability/handling-aspect-ratios-with-media-queries/).

## Put the system in the repository

A design system described in a chat message survives until the context gets
trimmed. Written into `_variables.scss`, it gets read fresh every time the agent
opens the file, and it gives you something to point at when you say "use the
existing tokens".

Keep it where the project already keeps such things and reference it in your
project instructions. See
[Managing Variables](/layout-assets-and-styling/dynamic-styling--variables/managing-variables/)
and [Writing Maintainable CSS](/layout-assets-and-styling/styling--scalability/writing-maintainable-css/).

:::danger[Token systems walk straight into the var() shorthand trap]

A token-driven system is exactly the code that wants to write
`padding: var(--space-md) var(--space-lg)` and
`border: 1px solid var(--color-border)`. Gameface does not resolve `var()` inside
a shorthand, and drops the whole declaration. Use the longhands, or use a
preprocessor variable substituted at build time instead of resolved at runtime.
The [negative ruleset](/building-with-ai/grounding-the-agent/#the-negative-ruleset)
carries this rule for good reason.

:::

## When you have no design yet

You still have options, listed here roughly by how well they worked for us.

A real design with a written token list beats everything else by a distance. Our
full-UI test started from a design created in
<Link href="https://claude.com/product/design">Claude Design</Link> plus a handoff
document covering the palette and its semantic rules, three type roles with a size
scale, exact spacing and geometry, and six named recurring ornaments. That turned
the agent's job into translation rather than invention, and the result held
together across eight screens.

An existing screen to match works nearly as well, assuming your project already
has one good screen. Say so explicitly and point at the file, because agents
extrapolate an existing system far better than they originate one.

A reference image will get you layout and hierarchy, which agents read from images
well. Fine visual detail is another matter, as the
[Match Tactics experiment](/building-with-ai/experiments/three-uis-with-an-agent/#behavior-arrived-in-better-shape-than-appearance)
shows.

Asking the agent to propose a system is the last resort, and it only works as a
separate step before any component work begins. Have it produce a token file,
review it yourself, correct it, and commit it. Whether the proposal is any good
matters less than you might think, because afterwards a system exists and
everything downstream stays consistent with it.

The one approach that reliably fails is starting from nothing and hoping coherence
emerges on its own.
