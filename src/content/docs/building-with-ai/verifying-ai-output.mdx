<Summary>
    Agent-written code is unusually good at passing casual inspection. It is idiomatic, commented, consistently named, and comes with a confident summary of what it does.

    None of that is evidence. This article is the checking that is - five layers, from cheapest to most expensive, and the one class of bug that only a <Highlight>production build in the Player</Highlight> will ever show you.
</Summary>

## Why normal review is not enough

Human-written bugs usually look like mistakes. Agent-written bugs look like
decisions. The code reads as though someone thought about it, because in a sense
someone did - it is just that the reasoning ran on assumptions you never saw.

Two habits are worth forming immediately:

* **Treat the summary as a claim, not a result.** "Added gamepad navigation and
  verified it works" means the agent believes it added gamepad navigation. Ask
  what it ran, or run it yourself.
* **Ask for the failure, not the confirmation.** "Show me the screenshot" beats
  "does it look right?", and "which assertions did you run and what did they
  return?" beats "did you validate it?".

## Layer 1 - Lint the source

The cheapest check, and it needs no agent involvement.
<Link href="https://frontend-tools.coherent-labs.com/eslint-plugin-gameface/getting-started/">eslint-plugin-gameface</Link>
flags unsupported patterns and data-binding mistakes across CSS, SCSS, HTML,
JSX/TSX and JavaScript. It ships pre-wired in the Gameface UI boilerplate and in
every framework template.

Run it in CI, not just in the editor. An agent that cannot see a red squiggle will
not fix one.

## Layer 2 - Read the engine console

The cheapest check that needs a running Player, and the one people forget. When
the stylesheet parser meets something it does not implement, it says so - a
warning per unsupported property, with the property named. The engine is telling
you exactly what it threw away.

The catch is that this only helps if something reads it. A build succeeds, a dev
server reports nothing, and an agent working from your editor never sees the
Player's console at all. With the [MCP server](/building-with-ai/gameface-mcp-server/)
connected, `get_console_logs` puts it in front of the agent, and it is worth
asking for by name after any styling work:

> Load the view and show me `get_console_logs` - any unsupported-property warnings?

Treat a warning naming a property you wrote as a definite bug, not a maybe. It
means that declaration did not survive, whatever the screenshot looks like.

## Layer 3 - Assert against the running engine

The console tells you what the engine rejected. It does not tell you whether what
survived actually lays out correctly. Three assertions do most of that work:

| Assertion | Catches |
| --- | --- |
| `assert_text_fits` | Clipped labels, overflowing values, text that fits in English and not in German |
| `assert_no_overlap` | A tooltip covering the number it explains; a badge sitting on top of a name |
| `assert_within_parent` | A panel running off the bottom at 21:9; a dropdown escaping its container |

`perf_lint` sits alongside them - a static check for layout patterns the Gameface
documentation names as expensive, with no timing involved and therefore no
flakiness.

The [Conductor skill](/building-with-ai/the-conductor-skill/) runs this battery
automatically as its validation stage. Without the skill, ask for it explicitly.

:::tip[Assertions are worth more than screenshots for the boring failures]
A two-pixel clip is invisible in a screenshot review and unambiguous in an
assertion. Use screenshots for the things only you can judge, and assertions for
everything measurable.
:::

## Layer 4 - Look at it yourself

Nothing in the toolchain evaluates whether the UI is *good*. The things you still
have to judge:

* **Visual coherence** - does this belong to the same interface as the screen next
  to it? See [Design first](/building-with-ai/design-first/).
* **Hierarchy** - does the most important thing read as the most important thing?
* **Feel** - transitions, timing, feedback on press. An agent will add a 300ms
  ease to everything and call it polish.
* **Focus order** - gamepad navigation that is technically present and moves in a
  nonsensical order. See [Spatial Navigation and Focus](/logic-and-interactions/interactions/spatial-navigation-and-focus/).

Ask for a screenshot at your real target resolution, and at your worst-case aspect
ratio. Then look at it next to an existing screen, not on its own.

## Layer 5 - Test the production build

This is the layer people skip, and it is the one that caught the worst bug we hit.

While building the Chart component, an overlay element that should have covered the
plot area was collapsing to 0x0 in the built page - and only in the built page.
The source wrote `left: 0; top: 0; right: 0; bottom: 0`. The CSS minifier folded
those four declarations into the `inset` shorthand, which Gameface does not
support, so the engine computed `auto` on all four sides and the element vanished.

Everything upstream passed:

* The source was valid, and lint had nothing to flag - `inset` never appeared in
  it.
* The dev server serves unminified CSS, so the shorthand did not exist there.
* Manual testing in the Player looked correct, because manual testing was against
  the dev server.

Note what is missing from that list: nobody had loaded a **production build** in
the Player and read its console. Layer 2 only helps against the artifact you
actually ship - a warning the engine never got the chance to print is no more
useful than one nobody read.

It cost a full development phase of misdiagnosis - scroll handling, coordinate
timing and event dispatch were all blamed before the real cause surfaced. What
found it was the end-to-end suite, which runs against `vite preview` rather than
the dev server.

Two rules come out of that, and they apply to human-written code just as well -
the agent simply gives you far more code per hour in which to hide one:

1. **Anything that must work in a shipped build has to be verified against a
   production build**, in the Player, not against a dev server.
2. **Source linting cannot catch what the build introduces.** The rules inspect
   your code; the minifier rewrites it afterwards.

The corollary for the source itself: never write four zero offsets on a stretched
element. `left: 0; top: 0; width: 100%; height: 100%` cannot be collapsed into
anything the engine rejects.

See [UI Testing](/polishing/debugging-profiling--testing/ui-testing/) for the E2E
setup, and [Layout Debugging](/polishing/debugging-profiling--testing/layout-debugging/)
when something has unexpectedly collapsed.

## Performance is its own pass

`perf_lint` and `perf_measure` tell you whether a screen is structurally expensive
or unusually slow against a recorded baseline. They do not tell you what your UI
costs inside your game, under real load, with the rest of the HUD alive.

Treat them as an early warning during development and do the real work with the
profiler - see [Performance and Memory Profiling](/polishing/debugging-profiling--testing/performance-and-memory-profiling/).

## A short checklist

Before you accept a screen an agent built:

* Lint passes in CI.
* The engine console is clean - no unsupported-property warnings naming anything
  you wrote.
* Layout assertions ran, and you have seen what they returned.
* You have looked at a screenshot at target resolution and at your worst aspect
  ratio.
* You have looked at it next to an existing screen.
* It has been opened from a **production build** in the Player.
* Gamepad or keyboard navigation has been driven by hand, not just declared
  present.
* You can name where every color, size and spacing value came from in your design
  system.
