<Summary>
    Bad code is cheap to fix, while <Highlight>well-built code for the wrong feature</Highlight> is expensive. "Build me an inventory screen" says nothing about gamepad navigation, empty states, item counts, or what happens when a name runs 40% longer in German, and an agent will invent an answer to every one of them.

    The Game UI Conductor refuses to start until those questions have answers and you have signed off on a written spec.
</Summary>

## The problem it solves

An agent handed a vague feature does not stop to ask. It fills the gaps with
whatever is most typical, writes several hundred lines against those assumptions,
and presents the result as finished. When the assumptions turn out wrong you
rarely get something you can tweak, because the interaction model and the state
shape are both built on them, and starting over usually costs less than repairing
it.

The Conductor spends the opening part of the conversation extracting requirements
instead, produces a spec you can read in two minutes, and touches no files until
you accept it.

:::note[Not every request needs this treatment]

The skill targets requests that arrive as a rough idea. Bug fixes, copy changes,
style tweaks, and any request that already names its interactions, states, and
data shape are out of scope, because they read like a spec already. Running a
clarification round on those is friction with no payoff.

:::

## The six stages

<Steps>

1. #### Reason about the relevant dimensions

    The skill consults a checklist of game-UI design dimensions covering
    interaction, animation and feedback, data and state, scale, accessibility,
    localization, sort and filter, and lifecycle. It then decides which ones
    actually apply. Not everything applies to everything, and the point is to
    catch the dimensions you did not mention.

    The checklist deliberately holds <Highlight>no engine-specific facts</Highlight>.
    Layout cost and CSS support belong to implementation time. This stage asks
    what the feature does, not how it gets built.

2. #### Clarify in rounds

    Three rounds at most, stopping earlier when nothing new surfaces.

    Round one asks everything relevant as a single batch rather than a drip of
    separate messages, and every question carries a sensible default so you can
    answer "use your judgment" and move on. Round two follows what round one
    opened up, so a yes to drag-and-drop leads to "what is the gamepad
    equivalent?" and "what happens if you drop it outside the panel?". Round three
    happens only when a real open question remains.

    Anything still unresolved becomes a stated assumption in the spec rather than
    another question.

3. #### Draft the spec and get sign-off

    A short document under fixed headings: Goals, Interactions, Data and state,
    Scale, Accessibility, Localization, Assumptions. It ends with a direct
    question asking whether this is what you want built.

    This stage is a <Highlight>hard gate</Highlight>. No code gets written until
    you accept the spec in the conversation. Rejecting it loops back with your
    correction, as many times as it takes.

4. #### Implement

    Normal rules apply from here. The agent follows
    `gameface://code-instructions` and calls `search_gameface_docs` while writing
    CSS and JavaScript, as covered in
    [Grounding the Agent](/building-with-ai/grounding-the-agent/).

5. #### Validate

    Given a Gameface MCP connection, the agent runs the layout assertions,
    `perf_lint`, and, when this is the dominant view, `perf_measure` against what
    it just built. Failures get fixed and the specific check re-run.

    With no connection available it says so plainly instead of skipping quietly.
    [Verifying What the Agent Builds](/building-with-ai/verifying-ai-output/)
    covers what to do with the results.

6. #### Report

    What was asked versus assumed, what you accepted at sign-off, what got built,
    and which checks passed or could not run.

</Steps>

## Running it

One set of files serves every client, but the trigger differs.

| Client | How it runs |
| --- | --- |
| **Claude Code** | Automatic, matching the skill's description against your request. You can also invoke it directly with `/gameface-conductor`. |
| **GitHub Copilot (VS Code)** | Automatic. Copilot's Agent Skills scans `.claude/skills/` alongside `.github/skills/`, so the file is picked up as-is. |
| **Gemini CLI** | Explicit only, since Gemini CLI has no auto-triggered skill concept. Run `/gameface-conductor <your request>`, and the command file injects the same skill content rather than duplicating it. |

Copy `.claude/skills/gameface-conductor/` into your own project to use it, plus
`.gemini/commands/gameface-conductor.toml` if you work in Gemini CLI. Both live in
the <Link href="https://github.com/CoherentLabs/Gameface-MCP">Gameface-MCP repository</Link>.

:::caution[The Gemini CLI path has not been run against a live session]

The TOML command file is structurally valid and matches Gemini CLI's documented
custom-command format, but nobody has confirmed it end to end. Treat it as
untested until you have run it yourself.

:::

## What surprised us about it

We expected the spec to be the useful part. The questions turned out to matter
more, and not because the agent knows game UI better than you do. It asks all of
them, every time, before anyone has invested in an implementation.

A Conductor round on a screen everybody called simple routinely surfaced two or
three decisions nobody had actually made, such as what the empty state says,
whether the panel pauses the game, and whether the list can hold 500 rows. Those
decisions were coming regardless. Answering them up front beats answering them
later, under more pressure, with code already written against the other
answer.

## Its limits

Answer every question with the default option and you get a spec full of
reasonable-sounding assumptions, which the build will then follow precisely.

The dimensions checklist covers behavior only, and nothing in it asks what the
panel should look like, which is why
[Design First](/building-with-ai/design-first/) is its own step.

Sign-off is also not review. Accepting a spec tells you the plan is right and says
nothing about the code that comes out the other end.
