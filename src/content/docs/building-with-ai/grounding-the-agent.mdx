<Summary>
    Inspecting a running Player catches mistakes after they are written. Grounding happens earlier, putting the right knowledge in front of the agent at the moment it writes the line.

    Two pieces handle it, and they pull in opposite directions. A <Highlight>documentation corpus</Highlight> answers questions on demand, while a <Highlight>negative ruleset</Highlight> sits permanently in context saying nothing except "never".
</Summary>

## Why the negative half carries more weight

A model asked to center some cards in a responsive grid will answer
`display: grid`. That answer is correct, common, and heavily represented in
everything the model learned from. Handing it a document explaining the Gameface
approach competes against that prior, and does not always win, because the model
first has to notice that this situation is unusual.

A negative rule takes the option away instead of arguing against it. "Never use
CSS Grid, Gameface has no grid layout" becomes something the model checks its own
output against, rather than a fact it has to remember to apply at the right
moment.

| | Documentation corpus | Negative ruleset |
| --- | --- | --- |
| Answers | "How do I do X in Gameface?" | "Is this line allowed at all?" |
| Delivery | Retrieved on demand, per query | Always in context |
| Content | Patterns, concepts, examples, trade-offs | A flat list of what the engine refuses |
| Written from | This guide | Engine feature detection |

Use both, since the ruleset stops the wrong thing from being written and the
corpus supplies the right thing to write instead.

## The documentation corpus

The corpus is this guide, restructured for retrieval. Prose written for someone
reading in order falls apart when you pull a paragraph out of sequence, and
pulling paragraphs out of sequence is exactly how an agent reads. So the same
knowledge is cut into chunks that stand on their own.

Each chunk carries metadata, which lets retrieval rank by more than keyword
overlap:

```markdown
[TOPIC: layout] [TYPE: concept] [SEVERITY: critical] [SOURCE: laying-out-the-screen.mdx]
## Flexbox-Only: Gameface Has No CSS Grid

Gameface's layout engine relies exclusively on the Flexbox model, powered by the
Yoga layout engine. CSS Grid is entirely absent, and all `grid-*` properties are
rejected by the parser...

> GAMEFACE CONSTRAINT: `display: grid`, `display: inline-block`, `display: contents`
> and `display: inline-grid` are rejected by the engine. Use `display: flex` exclusively.
```

`SEVERITY: critical` is what earns its place there. A search for "flexbox layout"
surfaces the constraint that breaks the screen ahead of the stylistic advice that
merely improves it.

divs.

### How the agent reaches it

With the MCP server connected, two routes exist. `search_gameface_docs` parses the
chunks once, scores them against a query, and returns only what is relevant. The
server's own instructions tell the agent to call it before writing markup, CSS, or
JavaScript. Each topic file is also exposed as a browsable resource at
`gameface://rag/<file>.md`, with `gameface://rag/index` listing them, for when the
agent wants a whole topic rather than an answer.

:::tip[A confident agent will skip the search]

Having the tool available is not the same as having it used. Adding a line to your
project instructions along the lines of *"call `search_gameface_docs` before
writing any CSS"* costs you nothing and measurably changes what the agent does.

:::

## The negative ruleset

The ruleset is one file, `prompts/negative-rules/negative-rules-injection.md`,
exposed by the MCP server as the `gameface://code-instructions` resource. Its
contents come from <Highlight>feature detection run against the engine</Highlight>
rather than from documentation, which is why it covers things no document would
think to mention.

A short "supported, use freely" section opens it. The rest is prohibitions:

| Section | Example rule |
| --- | --- |
| CSS, forbidden property families | Never use CSS Grid, multi-column, container queries, logical properties, scroll-snap, or view transitions |
| CSS, forbidden functions | Never use `oklch`, `lab`, or `color-mix`; never use `clamp`, `min`, or `max`; never use `repeating-linear-gradient` |
| CSS, partial-value restrictions | `border-style` rejects `dashed` and `dotted`, `box-shadow` rejects `inset`, `border-radius` rejects percentages |
| CSS, selector restrictions | `:has()`, `:checked`, `:disabled`, and `:focus-visible` parse but never match |
| HTML, forbidden tags and attributes | `<input type="checkbox">` is coerced to `type="text"`, `<table>` has no table layout, `<a href>` does not navigate |
| JavaScript, missing or stubbed APIs | No `fetch`, no `localStorage`, no `IntersectionObserver`, no Workers, no `AbortController` |

Two of those rules ruin more stylesheets than the rest combined.

The first is that `var()` does not work inside shorthands. Writing
`border: 1px solid var(--c)` drops the entire declaration rather than part of it,
and the same goes for `padding: var(--a) var(--b)` and
`transition: opacity var(--d) var(--e)`. The longhands work fine. An agent
building a token-driven design system reaches for the shorthand form every time,
and the screen comes out with no borders and no padding.

The second is that some selectors parse but never match. `:checked` and
`:disabled` produce no error and simply never apply, so a checkbox that reads
correctly in code renders permanently unchecked.

:::caution[Treat the ruleset as a snapshot of one engine version]

It reflects what feature detection found on the versions it ran against, and a few
entries carry an explicit "unverified" marker, among them `url()`, `image-set()`,
and `cross-fade()`, which could not be probed safely. Re-check it against the
<Link href="https://docs.coherent-labs.com/cpp-gameface/">Gameface documentation</Link>
when you upgrade, and when a rule contradicts what you observe, suspect the rule
before you suspect your code.

:::

## Using both without the MCP server

Neither piece requires the server. Both are plain Markdown in the repository, and
every agent has some form of always-loaded project instructions:

| Client | Where it goes |
| --- | --- |
| Claude Code | `CLAUDE.md` at the project root |
| GitHub Copilot | `.github/copilot-instructions.md` |
| Gemini CLI | `GEMINI.md` at the project root |
| Cursor | `.cursor/rules/` |

Paste the negative ruleset in wholesale, since it is written to be injected
verbatim, and reference the corpus files by path so the agent can open what it
needs. Losing on-demand retrieval hurts for the corpus, which is large. It costs
you nothing for the ruleset, which you want permanently in context anyway.

:::note[Keep it with the project, not in your personal config]

The ruleset describes the engine your team targets, so a new teammate cloning the
repository should inherit it without anyone telling them it exists.

:::
