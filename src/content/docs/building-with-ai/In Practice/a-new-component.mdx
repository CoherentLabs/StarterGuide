## Why this needed a different approach

A screen is a few hundred lines and one conversation. A component family is
thousands of lines across weeks, with a public API that other people will depend
on, and decisions in week one that constrain week four. Agents are weakest exactly
there: each session starts without the reasoning that produced the existing code,
and will happily re-open a settled question - or quietly contradict it.

The answer was a written specification held in the repository, at
`.specs/components/chart.md`. Not a plan the agent wrote and discarded - a
document that outlived every session, was reviewed by a person, and was updated
when reality disagreed with it.

## The spec as the real deliverable

Four parts of it did the heavy lifting.

### Decisions that are closed

A numbered table, introduced with a line that is doing real work:

> These were settled during the design interview and are not open for
> re-litigation during implementation; changing one means revising this spec.

Fourteen of them, each with its rationale. For example:

| # | Decision | Why |
| --- | --- | --- |
| D1 | d3 is a math library, not a renderer - import the generators, let Solid's `<For>` render every element | Keeps reactivity idiomatic and avoids d3's enter/update/exit fighting Solid's reconciler |
| D2 | All text is HTML, never SVG `<text>` | Gameface supports only basic `<text>` - no `<tspan>` - and HTML gives real fonts, wrapping and ellipsis |
| D3 | Interactivity is opt-in per component, off by default | Hit-testing is a measurable cost in a HUD; a presentational chart must be free |
| D5 | Animation is a JS tween over data *values*, re-running the geometry each frame | CSS cannot morph a path's `d`, and Gameface does not implement `element.animate()` |

The value is not that each decision is right. It is that a later session cannot
casually undo one without noticing that it is undoing something.

### Constraints gathered before any code

Section 3 lists what the engine cannot do, sourced from the Gameface SVG support
tables and the documentation corpus - no `<pattern>`, no SMIL, no
`<foreignObject>`, no SVG filters, `transform-origin` defaulting to `0 0` instead
of center, presentation attributes taking no units while the same properties set
via CSS require them.

Two of those changed the architecture rather than a detail:

* No `<tspan>` meant every label, tick and tooltip is an absolutely-positioned
  HTML element layered over the SVG.
* Animating primitive attributes being less reliable than animating a path meant
  **bars are rendered as `<path>`, not `<rect>`**.

Both were decided before a line was written. Discovering either one in week three
is a rewrite.

### Findings verified in the engine, not inferred

The section that turned out to be the most valuable is headed *"Verified against
Gameface Player 3.2.0.2 - checked directly in the engine while building phase 1,
not inferred from docs"*:

| Finding | Consequence |
| --- | --- |
| `getBoundingClientRect()` returns all zeros for SVG **child** elements; the root `<svg>` and HTML elements are fine | Geometry must come from JS, never from measuring marks - and an automated test driver has no coordinates to aim at |
| The `MouseEvent` constructor drops `clientX`/`clientY` - they read back as `0` | Synthetic events cannot test pointer coordinates; real input injection is required |
| `element.click()` is not a function | Tests must dispatch an event instead |
| Alpha values are quantized - `rgba(0,0,0,0.02)` computes to `0.004` | Anything relying on a near-invisible fill needs checking against what the engine kept |
| A scroll moves the plot without firing a resize | The cached plot rect has to refresh on pointer entry, not only on resize |

None of this is in any documentation, ours included. It exists because the agent
had a [live connection to the Player](/building-with-ai/gameface-mcp-server/) and
was asked to verify rather than assume - and because what it found was written
down where the next session would read it.

### A performance budget in numbers

Written before the first chart, not measured afterwards:

> Target ≤ 200 marks; warn in dev above 500. Exactly one tween signal write per
> frame regardless of mark count. `getBoundingClientRect` only inside the
> `ResizeObserver` callback - never during render, never in a `mousemove`
> handler. With `interactive` and `animation` both absent, a mounted chart has
> **zero** per-frame work and zero listeners.

A budget stated as a number is something an agent can hold itself to. "Make it
fast" is not.

## Delivery in phases

Six phases, each ending with a complete, shippable component rather than a layer
of scaffolding:

| Phase | Contents |
| --- | --- |
| 1 | Core hooks + `Chart.Pie` - sizing, data, tween, hover, palette, legend, labels, tooltip |
| 2 | `Donut`; extracted the shared radial engine |
| 3 | Cartesian core + `Bar` - scales, axes, grid, stacks, negatives |
| 4 | `Line` + `Area`; extracted the shared series engine |
| 5 | `Spider` |
| 6 | Polish - exit animations, draw-on reveal, label collision avoidance, leader lines |

The core hooks were built in phase 1 *against a real chart*, so later types wired
into them instead of retrofitting. Each phase ended with the full end-to-end suite
green - 29 specs after phase 3, 39 after phase 4, 47 after phase 5, 52 at the end.

That number is the discipline. A phase is not done because the agent says the
feature works; it is done when the suite passes.

## The bug that cost a phase

Phase 3's spec entry reads, in part: *"Also fixed the `inset` production bug."*
Behind that clause is the most useful thing in the whole project.

A hit overlay covering the plot area was computing to 0x0 - but only in a built
page. The source said `left: 0; top: 0; right: 0; bottom: 0`. The CSS minifier
folded those into the `inset` shorthand, which Gameface does not support, so the
engine computed `auto` on all four sides and the element collapsed.

Everything upstream was clean. The source was valid. Lint had nothing to flag,
because `inset` never appears in the source. The dev server serves unminified CSS,
so the bug did not exist there, and every manual check in the Player passed.

The agent spent a full phase misdiagnosing it - scroll handling, coordinate
timing, event dispatch - and the failing test was written off as a harness
problem. What actually found it was the end-to-end suite running against
`vite preview` rather than the dev server.

The spec now carries the generalisation as its own section:

> The dev server serves unminified CSS, so a minifier-introduced shorthand
> Gameface cannot parse will pass every manual check and only fail in a built
> page.

And the rule that came out of it: **never write four zero offsets on a stretched
element.** `left: 0; top: 0; width: 100%; height: 100%` cannot be collapsed into
anything the engine rejects.

## Recording when a decision was wrong

The open-items table tracks unresolved questions, and closed entries are struck
through with what happened. One is worth quoting because of what it admits:

> **O9** ~~Line draw-on animation.~~ Done in phase 6. `getTotalLength()` turned
> out to be genuinely absent, as suspected - but the earlier "drop it rather than
> approximate" call was **wrong**, because it assumed the length had to be
> measured off the DOM. The chart emits its own geometry, so the length is
> *derived*.

An earlier decision, recorded with its reasoning, was revisited months later and
found to have been based on a false premise - and could be, precisely because the
reasoning had been written down rather than lost with the session that produced
it. That is the whole argument for keeping a spec in the repository.

## What we took from it

* **For anything larger than a screen, the spec is the deliverable.** Code is
  cheap to regenerate; the reasoning behind it is not, and an agent will not
  remember it for you.
* **Have the agent verify engine behavior and write down what it finds.** The
  findings table was worth more than any single feature in the component.
* **Phase the work so every phase ends green.** It bounds how far a wrong turn
  can travel.
* **Do not trust a passing manual check.** The single worst bug was invisible
  everywhere except a production build under test.
* **A confident misdiagnosis can run for a long time.** The agent blamed three
  innocent subsystems in sequence, each plausibly. What stopped it was a test that
  ran against the right artifact - not better reasoning.
